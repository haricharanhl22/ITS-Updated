# HCAI-ITS — Complete Architecture Analysis

> Generated by inspecting the actual source at `ITS-Updated/` (backend FastAPI app + `frontend/` React app + `supabase/migrations/`). Every claim below is traced to a specific file/function. Where something described in the spec is **not implemented** or **implemented but not wired up**, this is called out explicitly.

## 1. Overall Architecture

### Components and why each exists

| Component | Technology | Why it exists |
|---|---|---|
| **Frontend** | React 18 + Vite, `react-router-dom`, `axios` | Renders the student UI (chat, dashboard, quiz), holds all UI state, talks to the backend over HTTP. Has zero business logic beyond presentation and optimistic UI. |
| **Backend API** | FastAPI (`backend/app/main.py`) | Single trust boundary. Owns the JWT/session validation, the RAG pipeline, the Groq API key, and all writes to Supabase. The **only** thing allowed to talk to Groq and to write mastery/message data. |
| **Database** | Supabase Postgres + `pgvector` extension | Stores everything: users, chat messages, textbook chunk embeddings, mastery scores, quiz content, and quiz history. Also runs one custom SQL function, `match_chunks`, for vector similarity search. |
| **LLM** | Groq (`llama-3.3-70b-versatile`) via the `groq` Python SDK | Generates the actual tutoring answer text. Called from `app/application/tutor_service.py::_call_groq_sync`. |
| **Embeddings** | `sentence-transformers` `all-MiniLM-L6-v2` (384-dim), loaded locally in the backend process | Turns textbook text and student questions into vectors for semantic (not keyword) retrieval. Runs in-process — no external embedding API. |
| **RAG pipeline** | `backend/app/rag/*.py` | Retrieves the textbook passages relevant to a student's question so the LLM answers from real course content instead of hallucinating. |
| **Auth** | Two systems coexist (see §11) — Supabase Auth (live) and a custom JWT/OTP system (built, not wired to the UI) | Supabase Auth is what the deployed app actually uses today; the custom system is dormant. |
| **Background services** | **None.** No Celery, no queue, no cron, no worker process. | Everything is synchronous request/response. Slow operations (embedding, PDF parsing, Supabase calls) are pushed onto a thread with `asyncio.to_thread(...)` purely so they don't block FastAPI's event loop — this is concurrency-within-a-request, not a background job system. |

### Why FastAPI sits between React and Supabase/Groq

The frontend **never** talks to Groq, and only talks to Supabase directly for its own authentication (`supabase.auth.signInWithPassword`, session refresh). All *domain* data (messages, mastery, quizzes, chunks) goes through FastAPI, because:

1. **Secret custody** — the Groq API key (`settings.groq_api_key`) and the Supabase service/anon key used for table writes live only in `backend/.env`. If React called Groq or wrote to `student_mastery` directly, those secrets (or a permissive RLS policy) would have to ship to the browser.
2. **Business rules must run somewhere trusted** — the BKU mastery-update formula (`assessment_service._compute_bku_update`), the adaptive difficulty threshold (`MASTERY_THRESHOLD = 0.65`), and the RAG retrieval + prompt construction (`tutor_service._build_prompt`) are non-trivial server logic. A thin Postgres RLS policy cannot express "run the student's question through a sentence-transformer, do a vector search, build a mastery-aware prompt, and call an LLM."
3. **ID translation layer** — Supabase Auth issues UUID-based users; every domain table (`student_mastery`, `messages`, `learning_events`) is keyed on a bigint `student_id` from the app's own `users` table. FastAPI's `get_current_student` dependency (`app/auth/auth_service.py`) is what bridges a Supabase JWT to that bigint ID (see §11) — this translation has to happen server-side.

## 2. Complete Request Lifecycle — "Student asks a question in chat"

This traces the **only path that is actually wired up and reachable from the UI** (see §11 for why other paths exist but are dead).

```
1.  Student types in the textarea and hits Enter / clicks send
      └─ frontend/src/pages/ChatPage.jsx :: sendMessage()   (line 79)

2.  Optimistic UI update
      └─ setMessages(prev => [...prev, userMsg])             (ChatPage.jsx:88-89)
      └─ setIsTyping(true)                                    (ChatPage.jsx:90)
      └─ (also bumps localStorage XP/streak counters, purely client-side, ChatPage.jsx:93-106)

3.  HTTP request
      └─ axios.post('/api/ask', { question }, { Authorization: Bearer <token> })
                                                              (ChatPage.jsx:109-111)
      token comes from useAuth() → AuthContext.jsx → supabase.auth session.access_token

4.  Vite dev-server proxy
      └─ frontend/vite.config.js  '/api' → http://localhost:8000

5.  FastAPI router
      └─ backend/app/api/ask.py :: ask(req, student_id=Depends(get_current_student))
         - validates question is non-empty
         - get_current_student (app/auth/auth_service.py) decodes the Bearer token:
             * tries custom HS256 JWT first → fails (Supabase-signed token)
             * falls back to supabase.auth.get_user(token) → gets email →
               looks up / lazily creates a row in the app's own `users` table →
               returns that row's bigint id as student_id (see §11 for full detail)

6.  Service layer
      └─ app/application/tutor_service.py :: get_answer(question, student_id)
         a. RAG retrieval:
              app/rag/retrieval.py :: retrieve(question, match_count=5, match_threshold=0.30)
                - app/rag/embeddings.py :: embed_one(question)  → 384-dim vector
                  (SentenceTransformer "all-MiniLM-L6-v2", lazy-loaded + lru_cache'd)
                - supabase.rpc("match_chunks", {...})            → top-5 chunks by cosine sim
                - falls back to `_keyword_fallback` (first N rows, no ranking) if the RPC
                  errors (e.g. not yet deployed)
         b. Concept detection:
              _detect_concept_from_chunks(chunks)  → keyword match over top-3 chunk text
              _detect_concept_from_text(question)  → keyword match over the question itself
              if both say "General" and the question looks like a continuation
              ("ok", "more", "why", ≤3 words) → _get_last_concept() looks at the student's
              last 5 assistant messages to infer topic continuity
         c. Mastery fetch:
              _get_mastery_sync(student_id, concept) — a direct supabase.table("student_mastery")
              query (NOT routed through mastery_repository.py — see §15)
         d. Conversation history:
              app/infrastructure/chat_repository.py :: get_recent_messages(student_id, limit=5)
              (fetches DESC newest-first, then reverses for chronological order)
         e. Build TutorContext dataclass (question, student_id, concept, mastery_score,
            retrieved_chunks, recent_messages)
         f. Prompt + LLM call:
              generate_groq_response(ctx)
                → _build_prompt(ctx)     builds system_prompt + user_prompt (see §8)
                → _call_groq_sync(...)   groq.Groq(...).chat.completions.create(...)
                  (wrapped in asyncio.to_thread)
                → on ANY exception (missing key, network, rate limit) →
                  falls back to _template_response(ctx) — a hand-written templated reply
         g. Persistence (best-effort, wrapped in try/except so a DB hiccup never breaks
            the chat response):
              chat_repository.insert_message(student_id, "user", question)
              chat_repository.insert_message(student_id, "assistant", answer)
         h. Cited-chunks formatting: top-3 chunks → { id, excerpt(250 chars), similarity, page_number }

7.  Response
      └─ ask.py wraps the dict into AskResponse pydantic model
         { response, concept, mastery_before, cited_chunks }
      └─ returned as JSON, HTTP 200

8.  React updates UI
      └─ ChatPage.jsx: setActiveConcept(data.concept), appends bot message
      └─ TypewriterText.jsx animates the already-complete string character-by-character
         (this is NOT token streaming from Groq — the full text already arrived in step 7;
         the typing effect is a pure client-side animation)
      └─ SourcesChip.jsx renders the cited_chunks as an expandable "N sources" panel
      └─ refreshMastery() (hooks/useMastery.js) fires a separate GET /mastery call to
         refresh the sidebar mastery bars — NOTE: mastery is only ever refreshed here,
         not actually changed, by chat (see §10)
```

No step is skipped from the spec's outline — the mapping is: React component → API request → FastAPI router → service layer → (RAG retrieval, DB queries) → Groq API → response → React re-render.

## 3. React Frontend Flow

- **Component that handles chat input:** `frontend/src/pages/ChatPage.jsx`. The `<textarea id="chat-input">` is controlled by `input` state; `handleInputChange` also auto-grows the textarea height. Enter (without Shift) calls `sendMessage()` (`handleKeyDown`, ChatPage.jsx:140-142).
- **How React stores the message:** local component state only — `const [messages, setMessages] = useState([])`. There is no global chat store (no Redux/Zustand/Context for chat) — messages live and die with the `ChatPage` component instance and are re-fetched from `GET /chat/messages` on mount.
- **How the API call is made:** raw `axios.post('/api/ask', { question }, { headers: { Authorization } })` called directly inside the page component (ChatPage.jsx:109). Note: there is a dedicated API client module (`frontend/src/api/tutor.js` with `apiAsk`, `apiGetMessages`, etc.) but **it is never imported by any page** — every page bypasses it and calls `axios` inline instead (see §15).
- **Endpoint called:** `POST /api/ask` for asking, `GET /chat/messages` for loading history on mount (ChatPage.jsx:56).
- **Loading state:** `sending` (disables the send button + shows a spinner) and `isTyping` (shows a three-dot "bot is typing" bubble while awaiting the HTTP response — this is not related to the token-by-token generation, it's just "request in flight").
- **How responses are rendered:** `renderMessageContent()` (ChatPage.jsx:145) manually splits the string on triple-backtick fences to render code blocks with a copy button, and on `` `inline code` `` / `**bold**` for lightweight formatting — this is a hand-rolled partial-markdown renderer, not a markdown library. New assistant messages play through `TypewriterText` once; once `typingDone[msg.id]` flips true, subsequent renders use the static `renderMessageContent` path instead.
- **Conversation history:** loaded once per mount from `GET /chat/messages` (returns last 10 rows per `chat_repository.get_recent_messages` cap), then appended to client-side as the conversation continues. There is no pagination/infinite scroll.
- **React hooks involved:** `useState`, `useEffect` (history load on mount, auto-scroll, active-concept-to-mastery sync), `useRef` (`messagesEndRef` for scroll-into-view, `textareaRef` for auto-resize), and the custom hooks `useAuth()` (`context/AuthContext.jsx`) and `useMastery()` (`hooks/useMastery.js`).
- **Files responsible:** `pages/ChatPage.jsx` (orchestration), `components/TypewriterText.jsx` (animation), `components/SourcesChip.jsx` (citations UI), `components/RadialProgress.jsx` (concept mastery ring), `hooks/useMastery.js` (mastery sidebar data), `context/AuthContext.jsx` (token).

## 4. FastAPI Backend Flow

Layering (present for every real feature except a few ad-hoc shortcuts noted below):

```
api/            → FastAPI routers. Parse HTTP, validate with Pydantic, call one service
                  function, translate results/exceptions to HTTP responses.
application/    → Business logic / use-cases ("services"). Orchestrates repositories,
                  RAG, and the LLM call. No FastAPI/HTTP imports here.
infrastructure/ → Repositories. Each file wraps one Supabase table with typed functions
                  (get/insert/upsert). This is the only layer that should import
                  `app.config.supabase_client`.
domain/         → Plain dataclasses/Pydantic models representing core concepts
                  (User, AssessmentQuestion, MasteryRecord, SubmitRequest, ...),
                  independent of the DB row shape or the HTTP schema.
schemas/        → Pydantic request/response models for the `auth` router specifically.
rag/            → Embedding model, chunking, pgvector retrieval, vector store upsert —
                  a vertical slice that several services (tutor_service, admin.py) call into.
config/         → `settings.py` (pydantic-settings, reads `.env`) and `supabase_client.py`
                  (single shared `Client` instance used everywhere).
```

**Exact call sequence for the two most important flows:**

*Ask a question:*
```
api/ask.py:ask()
  → auth/auth_service.py:get_current_student()          [dependency]
  → application/tutor_service.py:get_answer()
      → rag/retrieval.py:retrieve()
          → rag/embeddings.py:embed_one()
          → rag/retrieval.py:_search_sync()  [supabase.rpc("match_chunks")]
      → tutor_service.py:_detect_concept_from_chunks() / _detect_concept_from_text()
      → tutor_service.py:_get_mastery_sync()             [direct supabase call]
      → infrastructure/chat_repository.py:get_recent_messages()
      → tutor_service.py:generate_groq_response()
          → tutor_service.py:_build_prompt()
          → tutor_service.py:_call_groq_sync()            [groq.Groq(...)]
      → infrastructure/chat_repository.py:insert_message() ×2
```

*Submit a quiz:*
```
api/assessments.py:submit()
  → auth/auth_service.py:get_current_student()
  → application/assessment_service.py:submit_assessment()   [run via asyncio.to_thread]
      → assessment_service.py:_get_assessment_row()
      → infrastructure/mastery_repository.py:get_concept_mastery()
      → assessment_service.py:_determine_difficulty()
      → assessment_service.py:_get_questions()
      → assessment_service.py:_compute_bku_update()          [per question, in a loop]
      → infrastructure/mastery_repository.py:upsert_mastery()
      → infrastructure/learning_events_repository.py:insert_event()
```

**Why each layer exists:**
- Routers stay thin so the HTTP contract (status codes, request/response shape) is independent of business logic — you can unit-test `assessment_service.submit_assessment()` with plain dicts and no FastAPI test client at all (this is exactly what `backend/tests/test_assessment.py` does, mocking the repository functions and calling the service directly).
- Repositories isolate the Supabase query shape (table names, column names) from the rest of the app — if a table is renamed, only one file changes. In practice this discipline is inconsistent: `tutor_service.py`, `api/learning_events.py`, and `api/admin.py` all call `supabase.table(...)` directly instead of going through a repository (flagged in §15).
- `domain/` models decouple the wire format (Pydantic schemas in `api/*.py`) from internal business objects, so the API response shape can evolve without touching service logic, and vice versa.

## 5. Supabase Usage

All access goes through a single shared client: `app/config/supabase_client.py` — `supabase = create_client(settings.supabase_url, settings.supabase_key)`, imported by every repository and by several services directly.

| Table | Why it exists | Read from | Written from |
|---|---|---|---|
| **users** | App-level user identity (username, email, PBKDF2 password hash, role, verification flag). Not created by either migration file in `supabase/migrations/` — it must have been created ad hoc directly in the Supabase dashboard. | `infrastructure/user_repository.py` (`get_user_by_username`, `get_user_by_email`), `auth/auth_service.py` (Supabase-JWT fallback, lazy-creates a row) | `user_repository.py:create_user()` — called by `application/auth_service.py:register_user()` and by the lazy-provisioning branch in `auth/auth_service.py:get_current_student()`; `mark_user_verified()` after OTP/registration |
| **otp_tokens** | One-time codes for the (currently dormant) email/password registration flow. Also not in the migration files. | `infrastructure/otp_repository.py:verify_otp()` | `otp_repository.py:create_otp()` |
| **textbook_chunks** | RAG knowledge base — chunked textbook text + 384-dim pgvector embeddings. | `rag/retrieval.py` (via the `match_chunks` RPC, or the raw-table fallback), `api/admin.py:list_chunks()` | `rag/vector_store.py:upsert_chunks_batch()` — called from `api/admin.py:_ingest_pdf_sync()` (the live upload path) and the CLI scripts `rag/ingest.py` / `ingest_textbook.py` |
| **student_mastery** | Per-student, per-concept mastery score (0.0–1.0) driving both the chat tone and quiz difficulty. | `infrastructure/mastery_repository.py` (`get_mastery`, `get_weak_concepts`, `get_strong_concepts`, `get_concept_mastery`), and a **second, ad-hoc** query path in `tutor_service.py:_get_mastery_sync()` | `mastery_repository.py:upsert_mastery()` — called **only** from `assessment_service.py:submit_assessment()`. Chat never writes here. |
| **assessments** | One row per quiz topic (e.g. "Variables Quiz") — metadata only. | `assessment_service.py:_get_assessment_row()` | Nothing in the app writes this table — it is seeded by hand via SQL (`seed_data.sql` / migrations). |
| **assessment_questions** | The actual MCQ bank, tagged `difficulty` ('easy'/'hard') and `concept_name`. | `assessment_service.py:_get_questions()` | Seeded by SQL only (migration `002_add_difficulty_and_concept.sql` inserts sample hard questions) — no app endpoint creates questions. |
| **learning_events** | Immutable log of every quiz attempt (used for the dashboard sparklines/history). | `infrastructure/learning_events_repository.py:get_events_for_student()`, `api/learning_events.py:_fetch_events()` | `learning_events_repository.py:insert_event()` — called only from `assessment_service.py:submit_assessment()`, once per quiz submission (aggregate score, not per-question) |
| **messages** | Full chat transcript (student + assistant turns). | `infrastructure/chat_repository.py:get_recent_messages()` | `chat_repository.py:insert_message()` — called from `tutor_service.py:get_answer()` for every question/answer pair |

**CRUD pattern:** every repository function is a thin wrapper over the `supabase-py` fluent query builder (`.table(...).select/insert/update/upsert(...).eq(...).execute()`). Upserts (`student_mastery`, `textbook_chunks`) rely on a `UNIQUE` constraint (`(student_id, concept_name)` and `(page_number, chunk_index)` respectively) passed as `on_conflict=`. Because `supabase-py`'s client is synchronous, every call site in an `async def` FastAPI handler wraps the call in `asyncio.to_thread(...)` to avoid blocking the event loop — this pattern is used consistently in `chat_repository.py`, `assessments.py`, `learning_events.py`, and `admin.py`.

## 6. Chat Message Storage

- **Where:** the `messages` table (`chat_repository.py`, `TABLE = "messages"`).
- **When:** at the very end of `tutor_service.py:get_answer()` (step 6g in §2) — **after** the Groq call has already returned, not before. Both the user's question and the assistant's answer are inserted in the same call, back-to-back: `insert_message(sid, "user", question)` then `insert_message(sid, "assistant", answer)`. This write is wrapped in a `try/except` that only logs a warning on failure — so a Supabase outage will still let the student see an answer in the UI, it just won't be persisted for future history.
- **How history is retrieved:** `chat_repository.get_recent_messages(student_id, limit)` — fetches `ORDER BY created_at DESC LIMIT <cap>` then reverses the list in Python to restore chronological order. The function hard-caps `limit` at 10 regardless of what's requested (`cap = min(limit, 10)`), explicitly "to protect LLM context windows" (per the file's docstring).
- **How many previous messages are sent to the LLM:** **5**, not 10. `get_answer()` calls `chat_repository.get_recent_messages(sid, limit=5)` (`tutor_service.py:330`) specifically for prompt construction; the 10-message cap only applies to what the *frontend* loads into the chat window (`GET /chat/messages`, `chat.py:81`, and `GET /api/tutor/history/{student_id}`, `ask.py:71` — both request `limit=10`/`limit=5` respectively at the API layer, but the repository itself won't return more than 10 no matter what's asked).
- **Where implemented:** message shape and both endpoints live in `app/infrastructure/chat_repository.py`; the "last 5 for the prompt" decision is made in `app/application/tutor_service.py:get_answer()`; the "last 10 for the UI" decision is made in `app/api/chat.py:get_messages()`.

## 7. RAG Pipeline

```
PDF Upload                       (frontend/src/components/PDFUploader.jsx — built but
                                   not mounted on any route; only reachable by calling
                                   POST /api/admin/ingest-pdf directly, e.g. via
                                   backend/ingest_textbook.py CLI or Swagger UI)
   │  multipart/form-data
   ▼
api/admin.py :: ingest_pdf()
   │  validates .pdf extension, size > 100 bytes
   ▼
_ingest_pdf_sync()  (admin.py, run inside asyncio.to_thread)
   │
   ├─ 1. Text Extraction
   │      rag/pdf_loader.py :: extract_pages_from_bytes()
   │      uses `pypdf.PdfReader` (falls back to legacy `PyPDF2` if pypdf missing),
   │      returns [(page_number, page_text), ...], skipping pages under 30 chars
   │
   ├─ 2. Chunking
   │      rag/chunker.py :: chunk_text(page_text, page_number, concept)
   │      sentence/paragraph-aware splitter that preserves ``` code fences as atomic
   │      units; targets ~400 tokens (~533 words) per chunk with ~80-token
   │      (~107-word) overlap between consecutive chunks; concept label is derived
   │      from the uploaded filename (e.g. "python_functions.pdf" → "Python Functions")
   │
   ├─ 3. Embedding
   │      rag/embeddings.py :: embed(texts)
   │      SentenceTransformer("all-MiniLM-L6-v2"), lazy-loaded once via @lru_cache,
   │      normalize_embeddings=True (so cosine similarity == dot product),
   │      batch_size=32 → list of 384-dim float vectors
   │
   ├─ 4. Supabase pgvector upsert
   │      rag/vector_store.py :: upsert_chunks_batch(chunks, embeddings)
   │      writes to textbook_chunks in batches of 50 rows,
   │      on_conflict="page_number,chunk_index" (re-ingesting the same PDF updates
   │      rather than duplicates existing rows)
   │
   └─ returns IngestResponse { pages_found, chunks_built, chunks_saved, total_chunks }

────────────────────────────────────────────────────────────────────────────

At question time:

Similarity Search
   rag/retrieval.py :: retrieve(question, match_count=5, match_threshold=0.30)
     → embeddings.py :: embed_one(question)
     → supabase.rpc("match_chunks", { query_embedding, match_threshold, match_count })
       (SQL function defined in rag/setup.sql / supabase/migrations/001_initial_schema.sql:
        `1 - (embedding <=> query_embedding) AS similarity`, filtered > threshold,
        ordered by cosine distance, backed by an IVFFlat index)
     → on any RPC error, falls back to `_keyword_fallback()` which just returns the
       first N rows unranked (similarity hardcoded to 0.5) — a degraded-but-safe path

Prompt Construction
   tutor_service.py :: _build_prompt()   (full detail in §8)

Groq
   tutor_service.py :: _call_groq_sync()  → llama-3.3-70b-versatile

Final Answer
   returned to api/ask.py → AskResponse → React
```

**Files involved, end to end:** `frontend/src/components/PDFUploader.jsx` (UI, orphaned) → `app/api/admin.py` (HTTP entrypoint) → `app/rag/pdf_loader.py` → `app/rag/chunker.py` → `app/rag/embeddings.py` → `app/rag/vector_store.py` → `supabase/migrations/001_initial_schema.sql` (schema + `match_chunks` function, duplicated in `app/rag/setup.sql`) → `app/rag/retrieval.py` (query time) → `app/application/tutor_service.py` (prompt assembly).

**Dead parallel implementation:** `app/infrastructure/pdf/` (`pymupdf_reader.py` using `fitz`/PyMuPDF, `chunker.py` with a naive fixed-300-word splitter, `text_cleaner.py`) is a **second, unused** PDF pipeline. Nothing in `app/api/`, `app/application/`, or any test imports it — it's dead code sitting alongside the real pipeline in `app/rag/` (see §15).

## 8. What Is Sent to the LLM

This is assembled entirely in `app/application/tutor_service.py::_build_prompt(ctx: TutorContext)`.

**System prompt** (single string, sent as `{"role": "system", ...}`):

```
You are an expert Python tutor. Adapt your explanation based on the student's mastery level.
Always be encouraging and supportive.

Student Mastery — {concept}: {mastery:.2f}/1.0

Tone instructions: {tone}

Relevant Textbook Content:
{chunks_section}

Recent Conversation:
{history_section}
```

Where:
- **`{concept}`** — the detected topic (e.g. "Functions", or "General" if nothing matched).
- **`{mastery:.2f}`** — the student's current `mastery_before` score for that concept (0.00–1.00), read from `student_mastery` **before** this turn; chat never writes this value.
- **`{tone}`** — one of three fixed instruction blocks selected by mastery bracket:
  - `mastery < 0.4` → *"Use very simple language with real-world analogies. Break down every concept step by step as if explaining to a complete beginner. Include a concrete code example. At the end, gently suggest taking a quiz on this topic to build confidence."*
  - `0.4 ≤ mastery ≤ 0.7` → *"Use moderate detail with well-commented code examples. The student knows the basics — challenge them a little and introduce nuances. If mastery is below 0.6, suggest a quiz at the end."*
  - `mastery > 0.7` → *"Be advanced and concise. Skip the basics. Discuss edge cases, best practices, and Pythonic patterns. The student has strong mastery — treat them as a peer."*
- **`{chunks_section}`** — the **top 3** retrieved chunks (of the 5 retrieved), each truncated to 600 characters, formatted as `[Chunk N — page X]:\n<excerpt>`. If retrieval returned nothing: the literal string `"No textbook content retrieved."`.
- **`{history_section}`** — the **last 5** messages (both roles) from `messages`, each truncated to 200 characters, formatted `Student: ...` / `Tutor: ...` per line. If none: `"No prior conversation."`.

**User prompt** (sent as `{"role": "user", ...}`):

```
Student Question: {ctx.question}
```

**Metadata sent:** none beyond what's embedded in the text above — no student name, no user ID, no timestamp, no system/tool-call metadata, no conversation ID. The mastery number and concept label are the only "student context" the model receives; there is no explicit "student profile" object.

**Model call parameters** (`_call_groq_sync`):
```python
client.chat.completions.create(
    model=settings.groq_model,       # default: "llama-3.3-70b-versatile"
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user",   "content": user_prompt},
    ],
    temperature=0.7,
    max_tokens=1024,
    top_p=0.9,
)
```
No `stream=True` — the full completion is awaited before returning (the client-side "typewriter" effect is a fake, post-hoc animation of already-complete text, not real token streaming).

**Fallback:** if `GROQ_API_KEY` is unset, or the Groq call throws for any reason (network, rate limit, invalid key), `generate_groq_response()` catches the exception and calls `_template_response(ctx)` instead — a hand-written, non-LLM templated reply that echoes the first retrieved chunk (or a "please upload a textbook" message if none) with a mastery-appropriate opener and an optional quiz nudge. This means the tutor can appear to work even with zero LLM configured, just with lower-quality canned answers.

## 9. Groq Response Flow

1. **Where the response goes first:** back into `tutor_service.py::_call_groq_sync()` as `completion.choices[0].message.content.strip()` — a plain Python string.
2. **How it is parsed:** it isn't. No JSON parsing, no structured-output schema, no regex extraction. It's treated as opaque markdown-ish text end to end.
3. **Whether it is modified:** not on the backend. On the frontend, `ChatPage.jsx::renderMessageContent()` does a **presentation-only** transformation — splitting on ` ```code``` `, `` `inline` ``, and `**bold**` markers to produce styled JSX — but the stored/transmitted string itself is untouched.
4. **Whether it is stored:** yes — `chat_repository.insert_message(sid, "assistant", answer)`, immediately after generation, in the same request (§6).
5. **Which tables are updated:** only `messages` (one row for the user turn, one for the assistant turn). Chat, by itself, **never** touches `student_mastery` or `learning_events` — those are only updated by the quiz-submission flow (§10).
6. **How it is returned to React:** as the `response` field of the `AskResponse` Pydantic model (`app/api/ask.py`), alongside `concept`, `mastery_before`, and `cited_chunks`, serialized to JSON by FastAPI.
7. **How React displays it:** `ChatPage.jsx` appends a message object to state, marks it `isNew: true` and `typingDone[id] = false`, which triggers `<TypewriterText>` to animate the string in (with extra pauses after `.`/`!`/`?` and `,`); once done, `SourcesChip` renders the `cited_chunks` as a collapsible "N sources" panel below the bubble, and the mastery sidebar/ring refresh via `useMastery().refreshMastery()`.

## 10. Adaptive Learning Flow

All of this lives in `app/application/assessment_service.py`.

**Mastery calculation — Bayesian Knowledge Update (BKU), applied per question, not per quiz:**

```
weight = DIFFICULTY_WEIGHTS[(difficulty, is_correct)]
  ("easy", True):  0.8   ("easy", False): 1.2
  ("hard", True):  1.5   ("hard", False): 0.6

if correct:  new_mastery = mastery + GAIN_RATE(0.15) * (1 - mastery) * weight
if wrong:    new_mastery = mastery - LOSS_RATE(0.10) * mastery       * weight

clamped to [0.0, 1.0], rounded to 4 decimals
```

This runs once per question inside a loop in `submit_assessment()`, with `running_mastery` carried forward from one question to the next within the same submission — so a 5-question quiz applies the formula 5 times in sequence, compounding.

**Special-cases layered on top of the raw BKU result** (`submit_assessment`, lines ~218-228):
- A **perfect hard-tier quiz** (`difficulty_served == "hard"` and `correct_count == total`) forces `new_mastery = 1.0` outright, overriding the compounded BKU value.
- A **perfect easy-tier quiz** takes `max(old_mastery, running_mastery)` — i.e. it can't accidentally *decrease* mastery, but it also won't auto-jump to 1.0 the way a perfect hard quiz does.
- Otherwise the compounded BKU value is used as-is.

**Which functions update mastery:** only `assessment_service.py::submit_assessment()`, which calls `mastery_repository.py::upsert_mastery(student_id, concept, new_mastery)` — an upsert on `(student_id, concept_name)` that also increments an `attempts` counter and stamps `last_updated`.

**Which tables are modified by a quiz submission:**
- `student_mastery` — upserted with the new score (`mastery_repository.upsert_mastery`).
- `learning_events` — one new immutable row per submission: `{student_id, concept_name, score (the fraction correct for the whole quiz), assessment_id, created_at}` (`learning_events_repository.insert_event`). Note this stores the **aggregate** quiz score, not a per-question breakdown.

**How difficulty is selected — Easy vs Hard:**
- `MASTERY_THRESHOLD = 0.65`. `_determine_difficulty(mastery)` returns `"hard"` if `mastery >= 0.65`, else `"easy"`.
- On `GET /assessments/{concept}` (`assessment_service.get_assessment`): looks up the student's current mastery for that concept via `mastery_repository.get_concept_mastery`, computes the tier, and filters `assessment_questions` to that `difficulty`. If the filtered tier has zero rows (e.g. no hard questions seeded for that concept yet), it silently falls back to serving **all** questions regardless of tier.
- On `POST /assessments/submit`: difficulty is **re-derived** from the student's mastery **at submission time** (not passed by the client), so the scoring path independently re-fetches the same question set that would have been served — this prevents a client from claiming a different (easier) difficulty than what their mastery actually qualifies them for.
- The UI reflects this via `QuizPage.jsx` — each question card shows a `🔥 Hard` / `📗 Easy` badge from `question.difficulty`, and the result screen doesn't editorialize on difficulty beyond the score itself.

**Important nuance:** mastery is **only** moved by quizzes. Conversing with the AI tutor adapts its tone to the *existing* mastery score (§8) but never changes that score — there's no "the student seemed to understand" signal fed back from chat into `student_mastery`.

## 11. Authentication Flow

This is the most important — and most non-obvious — part of the system, because **three different auth mechanisms are implemented in the codebase, but only one and a half are actually reachable from the live UI.**

### 11.1 What's actually wired up today (the live path)

```
Registration/Login (frontend/src/pages/LoginPage.jsx)
   supabase.auth.signUp({ email, password })          — Register tab
   supabase.auth.signInWithPassword({ email, password }) — Sign In tab
   → these call Supabase's own managed Auth service directly from the browser via
     @supabase/supabase-js (frontend/src/api/supabaseClient.js). FastAPI is not involved
     in login/registration at all in this path.

Session
   frontend/src/context/AuthContext.jsx subscribes to
   supabase.auth.onAuthStateChange(...) and supabase.auth.getSession(), exposing
   { user, session, isAuthenticated, token: session?.access_token, logout }.

Protected Routes
   frontend/src/components/ProtectedRoute.jsx — redirects to /login if
   !isAuthenticated (or shows a spinner while isLoading). Wraps every route except
   /login in frontend/src/App.jsx.

Every subsequent domain API call (chat, mastery, quiz, learning-events)
   sends `Authorization: Bearer <supabase_access_token>` — a Supabase-issued JWT,
   NOT one minted by this backend.

Token Validation on the backend
   app/auth/auth_service.py :: get_current_student(authorization)
     Attempt 1: try to decode the token as this app's own custom HS256 JWT
                (jose_jwt.decode(token, settings.secret_key, algorithms=["HS256"]))
                → ALWAYS FAILS for a Supabase token, because Supabase signs its
                  JWTs with its own project secret, not settings.secret_key.
                  The exception is caught silently and execution falls through.
     Attempt 2: supabase.auth.get_user(token) — asks Supabase itself to validate
                the token and return the Supabase user record (email, UUID).
                → email is used to look up a matching row in this app's OWN
                  `users` table (user_repository.get_user_by_email).
                → if no such row exists yet, one is CREATED ON THE FLY right here:
                    username = email.split("@")[0] (deduped with a UUID suffix
                    if taken), password="" (empty hash — this shadow row can never
                    log in via the custom /auth/login path), role="student",
                    then immediately mark_user_verified(email).
                → returns that row's bigint `id`, stringified, as `student_id`.

     This bigint id is what every domain table (`messages`, `student_mastery`,
     `learning_events`) actually uses as its foreign key — Supabase's own UUID
     is never stored in those tables.
```

**In short: Supabase Auth owns "who are you", and FastAPI lazily mirrors each Supabase user into its own local `users` table the first time it sees them, purely to get a bigint ID to hang mastery/messages/events off of.**

### 11.2 What's fully implemented but currently dormant (not reachable from the UI)

A complete, independent username/password + email-OTP system exists on the backend:

- `POST /auth/register` → `application/auth_service.py::register_user()` → creates a `users` row (PBKDF2-SHA256 hashed password via `user_repository._hash_password`, 260,000 iterations) → generates a 6-digit OTP (`otp_repository.create_otp`, 10-minute expiry) → emails it via SMTP (`application/email_service.py::send_otp_email`).
- `POST /auth/verify-otp` → `verify_otp_and_login()` → validates the OTP, marks the user verified, issues this app's own HS256 JWT (`{"sub": username, "role", "id"}`, `settings.secret_key`, expires in `settings.access_token_expire_minutes` = 60 by default).
- `POST /auth/login` / `POST /auth/token` (OAuth2-form variant for Swagger UI) → `authenticate_user()` → same custom JWT.
- `GET /auth/me`, `POST /auth/logout` → operate on that custom JWT via a **separate** decode path (`api/auth.py::_get_current_user`, distinct from `get_current_student`).
- `POST /demo/login` + `GET /demo/personas` (`api/demo.py`) — issues the same custom JWT for one of three seeded demo personas (`ava_beginner`/`marcus_inter`/`priya_advanced`, seeded by `backend/seed_personas.py`), intended as a no-signup "try the product" entry point.

**None of this is reachable from the running app:** `frontend/src/api/auth.js` (the client for `/auth/*`) is never imported by any page. `frontend/src/context/PersonaContext.jsx` and `frontend/src/pages/PersonaScreen.jsx` (the client for `/demo/login`) exist and are fully built, but `PersonaProvider` is never mounted in `App.jsx` and no route points at `PersonaScreen` — they are orphaned. `backend/app/schemas/auth_schema.py` (a second, unused `LoginRequest`/`RegisterRequest` pair with `EmailStr`) is also dead — the live `auth.py` router imports from `schemas/auth.py` instead. This whole subsystem reads as either a legacy first pass before Supabase Auth was adopted, or scaffolding for a planned demo mode that was never routed in — either way, it is real, tested-looking, DB-backed code that a reader should not assume is "what the app does" without checking the frontend routes first.

### 11.3 JWT specifics

| | Custom JWT | Supabase JWT |
|---|---|---|
| Issued by | `application/auth_service.py::_create_access_token` | Supabase Auth (external) |
| Algorithm/secret | HS256, `settings.secret_key` | Supabase project's own signing key |
| Payload | `{sub: username, role, id}` | Supabase's own claims (`sub` = Supabase UUID, `email`, etc.) |
| Expiry | `settings.access_token_expire_minutes` (60 min default) | Managed by Supabase (with refresh via `supabase-js`) |
| Validated by | `api/auth.py::_get_current_user` (dead-path routes) or Attempt 1 of `get_current_student` | Attempt 2 of `get_current_student` via `supabase.auth.get_user()` |

## 15. Improvement Opportunities

*(Observations only — nothing below was changed.)*

### Security
- **`GET /mastery/{student_id}` has no auth dependency at all** (`app/api/mastery.py:33-43`) — any caller, authenticated or not, can read any student's mastery scores by supplying an arbitrary ID. Contrast with `GET /mastery` (no path param) which correctly scopes to the JWT's own student via `Depends(get_current_student)`.
- **`POST /api/admin/ingest-pdf` and `GET /api/admin/chunks` have no auth at all** — the code comment even says so directly ("No auth required for admin endpoints... Add bearer token check here if you need access control"). Anyone who can reach the API can pour arbitrary content into the RAG knowledge base or read chunk samples.
- Three parallel authentication systems (Supabase Auth, custom JWT/OTP, demo persona JWT) all converge into `get_current_student()`, but only Supabase Auth is exercised by the live UI. This makes it easy to reason incorrectly about "how login works" by reading only one file — the actual answer requires cross-referencing `App.jsx`'s route table against the backend routers (§11).

### Dead code (safe to delete or consciously re-enable)
- Frontend: `api/auth.js`, `api/tutor.js` (entirely unused API clients — every page calls `axios` inline instead, meaning endpoint URLs and error handling are duplicated ad hoc across `ChatPage.jsx`, `DashboardPage.jsx`, `QuizPage.jsx` rather than centralized once), `components/Sidebar.jsx`, `MessageBubble.jsx`, `QuizCard.jsx`, `BottomNav.jsx`, `context/PersonaContext.jsx`, `pages/PersonaScreen.jsx`.
- Backend: `app/schemas/auth_schema.py` (duplicate of `schemas/auth.py`, unused), `app/infrastructure/pdf/*` (a whole second, PyMuPDF-based ingestion pipeline that duplicates `app/rag/*` and is never called).
- `PDFUploader.jsx` is fully built and functional against a real endpoint but has no route/page mounting it — either wire it into an admin page or remove it.

### Consistency / maintainability
- **Two files literally named `auth_service.py`** (`app/application/auth_service.py` vs `app/auth/auth_service.py`) with different, non-overlapping responsibilities (login/register/JWT-issuance vs. per-request "who is this Bearer token" dependency). The naming collision invites importing the wrong one.
- **Repository-layer bypass:** `tutor_service.py::_get_mastery_sync`, `api/learning_events.py::_fetch_events`, and `api/admin.py::list_chunks` all call `supabase.table(...)` directly instead of going through `mastery_repository.py` / `learning_events_repository.py`, even though those repositories already exist and cover (most of) the same queries. This means the query logic for the same tables is now split across two places, and a schema change has to be hunted down in both.
- **Schema drift between the SQL migrations and the real deployed schema:** `supabase/migrations/001_initial_schema.sql` declares `student_mastery.student_id` and `messages.student_id` as `uuid`, and declares `learning_events.total_questions` / `correct_answers` columns — but every repository, service, and seed script in the codebase treats `student_id` as a bigint (matching the `users.id` autoincrement column, which isn't created by either migration file at all) and never populates `total_questions`/`correct_answers`. The migration files are therefore **not** an accurate description of the live schema — treat them as historical/aspirational rather than authoritative.
- `app/rag/setup.sql` and `supabase/migrations/001_initial_schema.sql` both define the `match_chunks` function and `textbook_chunks` table — two copies of the same DDL that could drift apart silently.

### Behavioral / design
- Mastery is **only** moved by quiz submissions, never by chat, even though the chat prompt is explicitly mastery-aware — a student who only ever chats (never quizzes) will see their mastery bars frozen at 0% forever, which may not match the product's implied "learn by conversing" framing.
- No true LLM streaming — `TypewriterText` fakes a typing effect over an already-fully-generated string, meaning perceived latency is (full Groq generation time) + (fake animation time), not reduced by streaming as it would be with `stream=True`.
- PDF ingestion is fully synchronous inside one HTTP request (`asyncio.to_thread` only prevents blocking *other* requests, it doesn't parallelize or background this one) — a large textbook could make `POST /api/admin/ingest-pdf` a very long-lived request with only a client-side fake progress percentage, no real progress events, and no resumability if it fails partway through a multi-batch upsert.
- `CORS` origins in `app/main.py` are hardcoded to four `localhost` dev ports — this will need to change for any non-local deployment and there's no environment-driven configuration for it today.
- The global `httpx` monkeypatch at the top of `app/main.py` (disabling HTTP/2 to work around a Windows-specific socket error) is applied unconditionally to every `httpx.Client`/`AsyncClient` in the process, including whatever the Groq SDK and `supabase-py` use internally — a narrow, single-platform fix with an app-wide blast radius.

### Not implemented (explicitly, since the spec implies they might exist)
- No streaming chat responses (confirmed above).
- No admin UI page for PDF upload, even though the component and endpoint both exist.
- No per-question breakdown stored for a quiz attempt — `learning_events` stores one aggregate score per submission, not which specific questions were right/wrong.
- No rate limiting, no request logging/analytics table, no background workers of any kind.
